# RAG Engine: контекстный поиск

Этот сервис принимает записи и документы, разбивает длинный текст на фрагменты, сохраняет исходник и версии в PostgreSQL и строит многоязычный векторный индекс. Поиск объединяет семантические совпадения и совпадения слов. Выход — фрагменты с идентификаторами источников, метаданными и версиями для приложения или отдельного ассистента. Сервис не рассчитывает карьерные рекомендации, бонусы или уровни навыков и не генерирует ответы LLM.

## Запуск на этом устройстве

Нужен Docker Desktop с Compose. Команды выполняются из этой папки:

```sh
cp .env.example .env
# Укажите абсолютный DATASET_DIR и замените секреты в .env.
docker compose up -d --build
docker compose ps
```

После старта `http://127.0.0.1:8000/docs` открывает интерактивное описание API. Для защищённых операций в Swagger нажмите **Authorize** и вставьте значение `RAG_API_KEY` из `.env`. `GET /health/ready` показывает доступность базы. На первом импорте многоязычная модель загружается в Docker volume `rag_models`; первый вызов может занять несколько минут. При последующих запусках кеш сохраняется.

Загрузка стартового набора:

```sh
docker compose exec engine python -m app.import_dataset
```

Импорт ожидает `employees.json`, `events.json`, `skills.json` и `activity_history.csv` в каталоге `DATASET_DIR`, смонтированном в контейнер только для чтения. По умолчанию здесь указан путь этого устройства; на другом компьютере замените его в `.env`. Повторный импорт не пересчитывает embeddings для неизменённых записей, изменённые атомарно заменяет, исчезнувшие из снимка записи удаляет. В каталоге данных хранятся 200 сотрудников, 40 мероприятий, 60 навыков, 32 профиля должностей и 2 743 записи участия. Все пять видов становятся отдельными источниками в namespace `career-quest`.

## API

Все операции, кроме `/health/*` и схемы API, требуют заголовок `X-API-Key`. Ключ предназначен для внутреннего приложения, его нельзя класть в браузерный код. Пока одна инсталляция использует один служебный ключ; авторизацию конечного сотрудника должно выполнять приложение перед вызовом сервиса. Поиск с персональными записями должен вызываться с ограничивающими `filters`, например `employee_id`. Для банковского пилота потребуется серверная проверка прав на уровне сервиса или отдельного шлюза.

| Метод | Адрес | Назначение |
|---|---|---|
| `PUT` | `/v1/documents` | Создать или заменить источник и все его чанки |
| `POST` | `/v1/documents/batch` | Создать или заменить до 100 источников одним запросом |
| `GET` | `/v1/documents/{source_id}?namespace=...` | Получить исходную запись |
| `DELETE` | `/v1/documents/{source_id}?namespace=...` | Удалить запись и все чанки |
| `GET`, `DELETE` | `/v1/documents?namespace=...&source_id=...` | Те же действия для идентификаторов с `/` и другими символами пути |
| `POST` | `/v1/lookup` | Получить записи по точным метаданным с постраничной выдачей |
| `POST` | `/v1/search` | Найти контекст с фильтрами |
| `POST` | `/v1/context` | Получить готовый текстовый блок и citations |
| `GET` | `/v1/stats?namespace=...` | Посчитать источники и чанки по типам |
| `GET` | `/health/live`, `/health/ready` | Проверить контейнер и базу |

Пример загрузки собственного источника:

```sh
curl -X PUT http://127.0.0.1:8000/v1/documents \
  -H "X-API-Key: $RAG_API_KEY" -H 'Content-Type: application/json' \
  -d '{"namespace":"career-quest","source_id":"rule:remote-work:v2","kind":"regulation","title":"Удалённая работа","content":"# Условия\nЗдесь будет утверждённый текст правила.","source_version":"2","metadata":{"department":"IT","owner":"HR"}}'
```

Пример поиска и фильтра по сотруднику:

```sh
curl -X POST http://127.0.0.1:8000/v1/search \
  -H "X-API-Key: $RAG_API_KEY" -H 'Content-Type: application/json' \
  -d '{"namespace":"career-quest","query":"Какие мероприятия посещал E0001?","kinds":["activity"],"filters":{"employee_id":"E0001"},"limit":5,"mode":"hybrid"}'
```

`POST /v1/context` принимает те же поля и `max_chars`, возвращает `context` и массив `citations`. Результат поиска включает `citation_id`, `source_id`, `chunk_index`, `kind`, `title`, `content`, `metadata`, `source_version`, время обновления и `matched_by`. Режимы: `hybrid` по умолчанию, `semantic`, `lexical`. `filters` — точное JSON-содержимое метаданных; `kinds` ограничивает типы. `as_of` ограничивает `effective_from`/`effective_to` для нормативных документов.

Если `as_of` не передан, используется текущий момент. Для исторического вопроса передайте явную дату. `POST /v1/lookup` принимает `namespace`, `kinds`, `filters`, `limit` и `cursor` и возвращает полные исходные записи и `next_cursor`; он подходит для выборки всех посещений одного сотрудника без зависимости от полноты семантического поиска. `POST /v1/documents/batch` принимает `{"documents":[...]}` с теми же полями, что единичный `PUT`.

Эндпоинт загрузки поддерживает произвольные типы источников: регламент, задача ОТК, событие, посещение и другие. Для часто меняющихся записей используйте стабильный `source_id` и повторяйте `PUT`; версия и метаданные войдут в новый индекс. Удаление удаляет чанки через связь в базе. Для полной синхронизации стартового набора служит команда импорта; новые источники приложения обновляются по API.

## Устройство поиска

Модель по умолчанию — локальная многоязычная MiniLM через FastEmbed/ONNX. Размерность индекса — 384. Текст документа делится по заголовкам и небольшим фрагментам примерно до 70 слов с перекрытием. Это ограничивает усечение на входе модели; длина в токенах различается по языкам, поэтому реальный банковский корпус потребует настройки на контрольных вопросах. PostgreSQL хранит исходники, JSON-метаданные, полнотекстовый индекс и векторы; pgvector использует HNSW. Два списка кандидатов объединяются reciprocal rank fusion. Поиск возвращает основания, а не достоверность ответа: потребителю нужно проверять цитаты и права доступа.

При смене модели с другой размерностью нужно создать новый индекс и переиндексировать данные. Переменная `EMBEDDING_MODEL` в этой версии предназначена для совместимой 384-мерной модели. База и кеш модели живут в Docker volumes; `docker compose down` их сохраняет, `docker compose down -v` удаляет.

## Перенос на другое устройство

Скопируйте репозиторий и датасет, укажите `DATASET_DIR` и секреты в `.env`, выполните запуск и импорт. Docker-контейнеры содержат код и зависимости; модель загружается при первом вызове, поэтому для закрытого контура банка её файлы потребуется заранее включить в разрешённый образ или внутреннее хранилище. Порт по умолчанию привязан к `127.0.0.1`, чтобы не открывать API наружу. Для доступа с другого устройства настройте внутренний reverse proxy, TLS и идентификацию вызывающего приложения.

## Проверка API

При запущенном Docker и загруженном стартовом датасете выполните из корня репозитория `python3 rag_engine/qa_e2e.py`. Сценарии создают отдельный временный namespace и удаляют его записи. Результаты последнего прохода — в [UltraQA отчёте](../docs/rag/ULTRAQA-REPORT.md).
