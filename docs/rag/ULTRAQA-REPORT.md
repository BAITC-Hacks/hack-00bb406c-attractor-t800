## Цель и границы

Проверить работающий Docker API на обычных и враждебных запросах, обновлениях, фильтрах и ошибках. Успех: корректные ответы и коды HTTP, неизменность основного namespace, отсутствие временных записей после проверки, контейнеры остаются доступными. Максимум пять циклов; три повторения одной неисправности останавливают работу. Не обращаться к внешним системам с данными и не выполнять разрушительных действий.

Исходное состояние: ветка `RAG-engine`; уже существующие изменения в `README.md`, `docs/`, `rag_engine/`, `.gitignore` сохраняются. В базе `career-quest` ожидаются 3 075 источников. Для записи использовать отдельный namespace `ultraqa` и удалить его записи после проверки. Команда `omx` недоступна, файл `ultraqa/templates/AGENTS.md` отсутствует: это ограничение инфраструктуры workflow, не дефект RAG Engine.

## Команды и циклы

Цикл 1: базовая проверка контейнеров и типов данных прошла, `qa_e2e.py` завершился кодом 1 на Q02. Причина — идентификатор с `/` принимался при PUT, но путь `GET /v1/documents/{source_id}` не позволял надёжно его передать.

Цикл 2: после исправления контейнер пересобран, `qa_e2e.py` завершился кодом 0. Все реализованные динамические проверки прошли. Повторный импорт завершился кодом 0: `Done: 3075 records, 0 updated, 0 removed`. `python3 -m compileall -q rag_engine/app rag_engine/qa_e2e.py` и `git diff --check` завершились кодом 0.

Команды с ограничением по времени: основной harness запускался через `subprocess.run(..., timeout=120)`; подвисание симулировалось `docker compose exec -T engine sleep 3` с `timeout=1`, после ограничения `/health/ready` вернул 200. Прямой вызов `timeout 120s ...` на macOS завершился кодом 127, потому что утилита `timeout` отсутствует; это ошибка оболочки стенда, исправленная запуском через Python, а не дефект продукта.

## Найденные неисправности

Один дефект API: путь источника мог содержать `/`, поэтому по URL с path-параметром запись нельзя было надёжно получить или удалить. В первом цикле тест завершился кодом 1; временная запись была удалена адресной командой SQL в собственном namespace. Данные `career-quest` не менялись.

## Исправления

В `rag_engine/app/main.py` добавлены `GET /v1/documents?namespace=...&source_id=...` и соответствующий `DELETE` с query-параметрами. В `rag_engine/README.md` описан этот адрес. `rag_engine/qa_e2e.py` использует его для произвольных ID и проверяет очистку. Второй цикл завершился без ошибки и не оставил записей.

## Остаточные риски

- Текущий служебный API key не выражает права конкретного сотрудника. Точные фильтры работают, но вызывающее приложение должно контролировать, кто вправе указать `employee_id`; для реальных банковских данных нужна серверная политика доступа.
- Пять контрольных ru/kk вопросов показывают работоспособность, но не доказывают качество поиска на будущем корпусе регламентов. Нужен размеченный набор реальных вопросов и ответственных источников.
- Сервис не имеет долгих фоновых заданий с API отмены/возобновления. Реальный обрыв HTTP во время записи не моделировался; проверены идемпотентные повторы и ограничение длительности команды.
- Модель загружается извне при первом импорте. Для закрытого банковского контура её нужно предварительно разместить во внутреннем образе или хранилище.
